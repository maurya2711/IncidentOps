# IncidentOps — Master Implementation Plan (All 11 Phases)

## Product Overview

**IncidentOps** is a production-grade enterprise Incident Management SaaS platform inspired by PagerDuty, Opsgenie, Better Stack, Datadog, and Linear. It is a full-stack monorepo with a Next.js 15 frontend and NestJS backend, deployed on Vercel + Railway + MongoDB Atlas.

---

## Architecture Summary

```
incidentops/                        ← Turborepo monorepo root
├── apps/
│   ├── web/                        ← Next.js 15 (App Router, React 19)
│   └── api/                        ← NestJS 10 (REST + WebSocket)
├── packages/
│   └── shared/                     ← Shared TypeScript types & enums
├── docker-compose.yml              ← Local dev environment
├── turbo.json
└── .github/                        ← CI/CD skeleton
```

### Phase 2 — Authentication Module

**Goal**: Complete auth system, JWT + Refresh Tokens, RBAC.

**Backend**
- `AuthModule` — login, register, refresh, logout, forgot-password, reset-password
- `UsersModule` — user CRUD, profile
- JWT strategy (access: 15min, refresh: 7d stored in httpOnly cookie)
- `JwtAuthGuard`, `RolesGuard`, `@Roles()` decorator
- Password hashing with bcrypt (12 rounds)
- Email verification token
- Password reset token (TTL: 1h)
- Rate limiting on auth endpoints
- DTOs: `LoginDto`, `RegisterDto`, `ForgotPasswordDto`, `ResetPasswordDto`
- User schema: name, email, password, role, avatar, isVerified, lastLogin, sessions[]

**Frontend**
- Route group: `app/(auth)/` — no sidebar layout
- Pages: `/login`, `/register`, `/forgot-password`, `/reset-password`
- `AuthProvider` — manages access token in memory, refresh via cookie
- `useAuth()` hook
- Middleware (`middleware.ts`) — protects `/dashboard/**`, redirects unauth
- Zustand `authStore` — user, isAuthenticated, loading
- React Hook Form + Zod schemas for all 4 forms
- "Remember Me" — extends refresh token lifetime
- Password strength indicator on register
- Smooth Framer Motion page transitions
- Beautiful split-screen layout (brand left, form right)

### Phase 4 — Incidents Module

**Goal**: Full CRUD incident management with rich detail view.

**Backend**
- `IncidentsModule` with full CRUD
- Schemas: `Incident`, `Comment`, `Attachment`, `TimelineEvent`
- Incident fields: title, description, severity (P1–P4), status (open/acknowledged/investigating/resolved/closed), assignee, service, tags, createdAt, updatedAt, resolvedAt, timeline[], comments[], attachments[]
- DTOs: `CreateIncidentDto`, `UpdateIncidentDto`, `AddCommentDto`
- Filtering: severity, status, service, dateRange, assignee
- Sorting: createdAt, severity, updatedAt
- Pagination: cursor-based
- File upload (Multer) for attachments
- Auto-generate timeline events on state change
- `IncidentsGateway` — Socket.IO events for real-time updates

**Frontend**
- `/dashboard/incidents` — Incident List (table + kanban toggle)
  - Advanced filter bar (multi-select: severity, status, service, date)
  - Global search within incidents
  - Sort controls
  - Pagination / infinite scroll
  - Bulk actions (acknowledge, close)
- `/dashboard/incidents/new` — Create Incident drawer/modal
- `/dashboard/incidents/[id]` — Incident Detail page
  - Header: severity badge, status badge, quick-action buttons (Acknowledge, Resolve, Escalate)
  - Metadata sidebar: assignee, service, tags, created/updated timestamps
  - Timeline tab — vertical event timeline, auto-updating
  - Comments tab — threaded comments, markdown support
  - Attachments tab — file list, upload dropzone
  - Related Incidents section
- Edit Incident — inline editing with optimistic updates
- Delete with confirmation dialog
- Assign to user — searchable user picker

### Phase 5 — Services Module

**Goal**: Service registry with health monitoring.

**Backend**
- `ServicesModule` — CRUD for services
- Schema: name, description, owner (team), status (operational/degraded/partial/outage/maintenance), uptime%, latency (ms), errorRate (%), dependencies[], statusBadgeToken
- `ServiceMetrics` — time-series data points (stored in MongoDB, queried with aggregation)
- API: list services, get service, update service, get service metrics, get service incidents

**Frontend**
- `/dashboard/services` — Service List
  - Status filter tabs (All / Operational / Degraded / Outage)
  - Responsive card grid — each card shows: name, status badge, uptime %, latency, error rate, team owner
- `/dashboard/services/[id]` — Service Detail
  - Header: service name, status badge, quick-edit
  - Health metrics bar: uptime %, avg latency, error rate, p95 latency
  - Latency chart (line chart, 7d/30d toggle)
  - Error Rate chart
  - Incident History table (filtered to this service)
  - Dependencies graph (simple dependency list with status)
  - Status Badge embed code (copy-to-clipboard)
- Create / Edit Service — form drawer

**Backend**
- `TeamsModule` — team CRUD

- Member schema: userId, role (owner/admin/member/viewer), joinedAt, availability
- Invite flow: email invite → token → accept → join team
- `PermissionsGuard` — team-scoped RBAC

**Frontend**
- `/dashboard/teams` — Team List (card grid)
- `/dashboard/teams/[id]` — Team Detail
  - Members table: avatar, name, email, role badge, availability status, current incident
  - Invite User — email input + role picker → sends invite email
  - Edit member role — dropdown inline
  - Deactivate User — confirmation dialog
  - Permissions matrix — what each role can do (read-only view)
  - Current Active Incidents — list of incidents assigned to this team

**Backend**

**Frontend**

  - **MTTR** (Mean Time to Resolve) — KPI card + trend line chart

### Phase 8 — Real-Time Module (Socket.IO)

**Goal**: Live updates across the entire application.

**Backend**
- `EventsGateway` — Socket.IO with JWT auth handshake
- Namespaces: `/incidents`, `/services`, `/notifications`
- Events emitted:
  - `incident:created`, `incident:updated`, `incident:status_changed`, `incident:comment_added`
  - `service:health_changed`
  - `notification:new`
  - `dashboard:metrics_updated`
- Redis adapter for Socket.IO (horizontal scaling)
- Room-based broadcasting (org-scoped)

**Frontend**
- `useSocket()` hook — singleton connection, auto-reconnect, JWT auth
- `useIncidentSocket()` — auto-invalidate TanStack Query on incident events
- `useServiceSocket()` — live service health updates
- `useDashboardSocket()` — live KPI card updates
- Toast notifications on new critical incidents
- Live timeline entries append without page refresh
- Service health grid live badge updates

### Phase 9 — Notifications Module

**Goal**: Multi-channel notification system.

**Backend**
- `NotificationsModule`
- Schema: userId, type (incident_created/assigned/commented/resolved/service_down), title, body, link, read, createdAt
- Email via Nodemailer (SMTP/SendGrid)
- BullMQ queue for async email dispatch
- User preferences: which events trigger email vs in-app
- Mark read (single + bulk)
- Pagination

**Frontend**
- `NotificationBell` — badge with unread count, animated on new notification
- `NotificationDrawer` — slide-in panel from header
  - Notification list with icon by type, timestamp, read/unread state
  - "Mark all as read" button
  - Infinite scroll
  - Click → navigate to relevant resource
- Toast system (Sonner) — critical incident toasts, success/error feedback
- Unread count in browser tab title

### Phase 10 — Settings Module

**Goal**: Comprehensive user and organization settings.

**Backend**
- `SettingsModule` — user preferences CRUD
- `SessionsModule` — list and revoke active refresh token sessions
- `ApiKeysModule` — generate, list, revoke API keys (SHA-256 hashed)
- Update profile (name, avatar upload via Multer)
- Change password (current + new + confirm)
- Security log (login events)

**Frontend**
- `/dashboard/settings` — settings shell with tab sidebar
- **Profile Tab** — avatar upload, name, email, timezone, bio
- **Password Tab** — change password form, password strength meter
- **Theme Tab** — Light / Dark / System toggle with live preview
- **Notifications Tab** — per-event toggles (Email / In-App) with category groups
- **Security Tab** — 2FA placeholder, login activity log, trusted devices
- **Sessions Tab** — table of active sessions (device, IP, location, last seen), revoke individual or all
- **API Keys Tab** — generate named API key, list keys (masked), copy on creation, revoke

### Phase 11 — Public Status Page

**Goal**: Publicly accessible status page (no auth required), SEO optimized.

**Backend**
- `StatusPageModule` — public endpoints (no auth guard)
- Endpoints: GET `/status` (overall), GET `/status/services`, GET `/status/incidents`, GET `/status/uptime`
- Maintenance window schema: title, startAt, endAt, affectedServices[]

**Frontend**
- Route: `app/(public)/status/` — separate layout, no sidebar/auth
- `StatusPage` — `status.incidentops.io` or `/status` path
  - **Overall Status Banner** — "All Systems Operational" / "Partial Outage" etc.
  - **Service Health Grid** — current status per service, colored status pill
  - **90-Day Uptime Bars** — GitHub contribution-style colored day bars
  - **Active Incidents** — public incident title + severity + timeline (internal details hidden)
  - **Maintenance Windows** — upcoming + past scheduled maintenance
  - **Incident History** — last 30 days of resolved incidents
  - Auto-refresh every 60 seconds
  - RSS feed link
  - Subscribe to updates (email input)
- **SEO**: `<title>`, `<meta description>`, Open Graph tags, `robots.txt`, `sitemap.xml`, structured data (JSON-LD)
- Responsive: mobile-first, works on all devices
- No auth, no sidebar — completely standalone page

## Deployment Architecture

```
Vercel (web)  ←→  Railway (api)  ←→  MongoDB Atlas
                      ↕
                Redis Cloud (BullMQ + Socket.IO adapter)
```

- All secrets via environment variables (never committed)
- HTTPS everywhere
- API behind Railway private networking
- Rate limiting on all public endpoints
- CORS restricted to Vercel domain
